Question. Is this the right set of methods, events and frames for protocol v1, now that it must carry everything cc's frontend asks of a host: sessions, the planes list, plane creation, files and source control? Push a stub daemon through the awkward cases and watch every message that crosses the wire.

What changed from v1. The daemon is the host agent: on a remote host it is the only bitplane process, so it also serves planes.*, plane creation as a job that outlives the client, fs.* and git.*. Sessions gained seq, key, foreground and session.busy. v1 walkthroughs are kept; new ones start at "Startup".

The model. One host runs one session daemon. Two clients reach it: A is cc on the same machine (Unix socket), B is a second device going through the gateway (WebSocket → bpg-server → ssh → daemon). A client opens sessions (a shell in a plane), attaches to watch and type, and acknowledges the bytes it has drawn so the daemon knows how far ahead it may run. Sizes are in KiB; a program "printing 512 KiB" stands in for real output.

Strawman choices to react to (all live in the logic module, nothing in the page):

  • One hello per connection negotiates the version; no per-request version stamp.
  • Binary frames are addressed by a small per-connection attachment id, not by session id.
  • Typing is a binary INPUT frame (no reply); everything else is JSON-RPC.
  • Flow control: 128 KiB window per attachment, 256 KiB queue; overflow marks the attachment behind, its queue is dropped, and once it catches up it gets a fresh SNAPSHOT instead of the lost bytes.
  • Events: every connection that said hello gets session.changed / session.removed for the whole host. No subscribe call.
  • Agent state is a field of the session, not its own method family.
  • Two event styles, as in cc today: sessions, planes and jobs are broadcast to every connection; files and git are scoped watches (fs.watch, git.watch), one scope per connection that each call replaces, dropped on disconnect.
  • Plane creation is plane.create → a job with phase, status and a streamed log (job.log). The daemon keeps it after the starting client leaves; job.list finds it again. Phases assume bp create reports structured progress.
  • Opening in VS Code is not a host call: the client hands off to its own editor (Remote-SSH).
  • Gateway: one WebSocket per host, host chosen by URL path; after hello messages pass through byte-for-byte. The only addition is host in the hello result.
