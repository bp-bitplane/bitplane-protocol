Question. Is this the right set of methods, events and frames for protocol v1, now that the daemon is split into modules, each owning one namespace? Push a stub daemon through the awkward cases and watch every message that crosses the wire.

What changed from v2 (from How sessiond is split into modules):

  • One namespace per module: root (hello, job.*), session.* + session.attachment.*, agent.claude.*, plane.*, fs.*, git.*. bp.dispatch is now plane.dispatch.
  • hello lists modules in capabilities[], with a reason when one is missing (no bp, git or claude). Calling a missing module returns MODULE_UNAVAILABLE. Availability is probed once, at daemon start.
  • No module depends on planes. session.open { root, env, plane? }: plane is an opaque id the daemon stores but never reads. fs.* and git.* take paths. Git is per repo path; the client gets member paths from plane.list.
  • A plane folder vanishing under a running session: session.changed sets rootGone, the shell keeps running, session.restart is refused, watches end with fs.changed / git.changed { path, gone: true }.
  • Agent state left the session: agent.claude.* owns it, keyed by agent session with an optional session reference.
  • A running job dies with the daemon and comes back failed (daemon restarted), the plane left partial.

The model. One host runs one daemon. Two clients reach it: A is cc on the same machine (Unix socket), B is a second device going through the gateway (WebSocket → bpg-server → ssh → daemon). Sizes are in KiB; a program "printing 512 KiB" stands in for real output.

Strawman choices kept from v2: one hello per connection; binary frames addressed by a per-connection attachment id; typing is a binary INPUT frame; 128 KiB flow window, 256 KiB queue, then drop and resnapshot; sessions, agents, planes and jobs are broadcast, fs and git are scoped watches (one scope per module per connection, each call replaces it); one WebSocket per host through the gateway.
